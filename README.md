# Tolvira

> **Universal Online Utility Platform** — 1,000+ utilities powered by client-side WebAssembly (WASM) and Rust.

A modular, production-ready, universal online utility platform designed to scale to 1,000+ utilities (PDF tools, image editors, video converters, audio processors, developer utilities, text transforms, and calculators).

Heavy file and computation tasks run entirely **client-side in the browser** using WebAssembly (WASM) and isolated Web Workers, providing zero server upload latency, complete user privacy, and zero server bandwidth costs for file processing. The backend operates as a lightweight metadata registry, configuration service, and engine manifest provider.

## 2. Key Architectural Responsibilities

### Frontend
- **Zero Heavy Processing on Main Thread**: Heavy operations execute in Web Workers using transferable `ArrayBuffer` objects.
- **Dynamic On-Demand Loading**: Individual utility UIs and WASM engines are lazy-loaded only when navigated to.
- **Version-Aware Caching**: Engine binaries are cached in the browser Cache API with fallback to memory, verified against cryptographic SHA-256 hashes.
- **Resilient Fallback**: Operates both connected to the backend API or 100% standalone for static edge deployments.

### Backend (Rust / Axum)
- **Central Utility Registry**: Manages metadata, categories, features, and status across all 710+ tools.
- **Engine Version Management**: Generates engine manifests, capabilities, dependencies, and SHA-256 hashes.
- **Zero File Upload Processing**: Intentionally does not accept file uploads for utilities that run client-side.
- **REST Endpoints**:
  - `GET /api/v1/health` — Service health and available engines
  - `GET /api/v1/tools` — Paginated tool catalog with filtering
  - `GET /api/v1/tools/:id` — Single tool metadata + required engine config
  - `GET /api/v1/categories` — Catalog categories with tool counts
  - `GET /api/v1/engines` — List of registered WASM engines
  - `GET /api/v1/engines/:id` — Specific engine manifest & capabilities

## 3. Getting Started & Local Development

### Requirements
- **Node.js**: v22+
- **pnpm**: v10+
- **Rust**: 1.80+ with `wasm32-unknown-unknown` target (`rustup target add wasm32-unknown-unknown`)

### Initial Setup

```sh
# 1. Install dependencies
pnpm install

# 2. Build the WASM processing engines
pnpm run build:engines

# 3. Build the backend binary
pnpm run build:backend
```

### Running Locally

You can run both the frontend and backend simultaneously or independently:

```sh
# Run the Frontend (Vite server on port 5173)
pnpm run dev:frontend

# Run the Backend (Axum REST API on port 5001)
pnpm run dev:backend
```

- Frontend App: [http://localhost:5173](http://localhost:5173)
- Backend API: [http://localhost:5001/api/v1/health](http://localhost:5001/api/v1/health)

## 4. WASM Engine Compilation

See `engines/README.md` for the engine protocol and `CONTRIBUTING.md` for the
code-quality rules (no panics, documented public API, formatting and lint
commands) that CI enforces on the engine workspace.


All engines live in `engines/` and are built as cdylib crates for WebAssembly:

```sh
# Rebuild all engines at once
pnpm run build:engines

# Or build via cargo directly
cargo build --manifest-path engines/Cargo.toml --workspace --target wasm32-unknown-unknown --release
```

WASM binaries are compiled with size and performance optimizations (`opt-level = "z"`, LTO enabled, symbols stripped) and output to `frontend/public/engines/`.

## 5. How to Register a New Utility

Most utilities need **no UI code at all**: every engine action is exposed
through the generic `EngineToolRunner`, whose form is generated from the Rust
action enum (`shared/data/engine-schemas.json`). Users get file pickers,
number inputs, switches, selects, colour pickers and – for expressions – a
calculator keypad; results come back as download cards, previews, tables and
stat cards. To publish a tool:

1. implement (or pick) the engine action in `engines/<crate>` and document its
   payload fields (the doc comments become labels, help text and option lists);
2. map the catalog id / registry slug in `scripts/generate-engine-tools.py`
   (`MAP`, `PRESETS`, `REGISTRY_ALIASES`) and run `pnpm run generate:engine-tools`;
3. `pnpm run test:engines:ui` verifies the generated form against the real
   `.wasm`.

The steps below are only for tools that need a *dedicated* interactive UI
(canvas editors, live previews) on top of the generic runner.

### Step 1: Add Tool Metadata
Add the tool entry to `shared/data/tools.json`:

```json
{
  "id": 711,
  "name": "Markdown to HTML",
  "slug": "markdown-to-html",
  "category": "Text Tools",
  "status": "available",
  "description": "Convert Markdown text to sanitized HTML instantly in your browser."
}
```

### Step 2: Create the Tool UI Component
Create a lightweight component in `frontend/src/tools/text/MarkdownTool.tsx`:

```tsx
import React, { useState } from "react";
import { WorkerManager } from "../../services/worker-manager";
import type { ToolDefinition } from "../../types";

export const MarkdownTool: React.FC<{ tool: ToolDefinition }> = ({ tool }) => {
  const [input, setInput] = useState("# Hello World");
  const [output, setOutput] = useState("");

  const convert = async () => {
    const workerMgr = WorkerManager.getInstance();
    const result = await workerMgr.executeTask(
      "text-engine",
      tool.engine!.url,
      "convert_markdown",
      { text: input }
    );
    setOutput(result.html);
  };

  return (
    <div>
      <textarea value={input} onChange={(e) => setInput(e.target.value)} />
      <button onClick={convert}>Convert</button>
      <div dangerouslySetInnerHTML={{ __html: output }} />
    </div>
  );
};
export default MarkdownTool;
```

### Step 3: Register in Dynamic Tool Map
In `frontend/src/tools/index.ts`:

```typescript
export const TOOL_COMPONENTS = {
  // ... existing tools
  MarkdownTool: lazy(() => import("./text/MarkdownTool")),
};
```

In `frontend/src/registry/tool-registry.ts` and `backend/src/registry/tool_registry.rs`, map `"markdown-to-html"` to `text-engine` and `MarkdownTool`.

## 6. How Multiple Utilities Share Engines

Multiple utilities share a single WASM engine to prevent duplicate downloads and minimize memory consumption:

```
┌─────────────────────────────────┐
│           text-engine           │
│   (312 KB WASM, cached once)    │
└───────┬──────────────┬──────────┘
        │              │
        ▼              ▼
┌──────────────┐ ┌──────────────┐
│  Case Conv.  │ │ Word Counter │
└──────────────┘ └──────────────┘
```

Both utilities invoke `WorkerManager.getInstance().executeTask('text-engine', url, action, payload)`. The worker reuses the already compiled WASM module and routes tasks through the action dispatcher.

## 7. How to Add a New Processing Engine

1. Create a crate in `engines/<engine-name>/` with `Cargo.toml`:
   ```toml
   [package]
   name = "my-engine"
   version = "1.0.0"
   edition = "2021"

   [lib]
   crate-type = ["cdylib", "rlib"]

   [dependencies]
   serde = { version = "1.0", features = ["derive"] }
   serde_json = "1.0"
   engine-shared = { path = "../shared" }
   ```
2. Add member to `engines/Cargo.toml`.
3. Implement `alloc`, `dealloc`, `result_len`, and `execute` using `engine-shared`.
4. Register the manifest in `backend/src/registry/engine_registry.rs` and `frontend/src/registry/engine-registry.ts`.
5. Compile via `pnpm run build:engines`.

## 8. Production Deployment

### Static Frontend (CDN / Object Storage)
```sh
pnpm run build:frontend
```
The static distribution is written to `frontend/dist/public/`. It includes:
- Pre-rendered static SEO HTML shells for all 710 utilities
- Bundled CSS and lazy-loaded tool chunks
- Versioned WASM binaries under `/engines/` and `/search.wasm`

Deploy the directory to Cloudflare Pages, Vercel, Netlify, or an S3/CloudFront bucket.

### Backend Service (Docker / Container)
```sh
pnpm run build:backend
```
The compiled standalone binary is located at `backend/target/release/dev-toolbox-backend`.
Run behind Nginx or a cloud load balancer with `HOST=0.0.0.0 PORT=5001 ./dev-toolbox-backend`.
